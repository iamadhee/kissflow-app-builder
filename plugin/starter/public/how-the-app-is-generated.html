kf-app-author · generation pipeline

How a Kissflow app is generated — from a BRD to a rich, role-aware UI

A requirements document goes in. Out comes a complete, working Kissflow application — data models, processes, child tables, workflows, roles, permissions, pages and navigation — and a rich React runtime UI composed over it. No metadata is hand-written; every artifact is built deterministically and verified.

The big picture

Two pipelines run back-to-back. Pipeline A turns a BRD into a live Kissflow app (the system of record). Pipeline B reads that live app back and composes a rich React UI over it. The first builds the truth; the second builds the experience.

DEEP DIVE

The kf-app-author agent system — detailed spec

A blackboard architecture: every agent reads and writes one shared file, lib/app-spec.json (the App-Spec IR). Each owns exactly one slice and reads the slices beneath it. The agents reason about intent; the engine compiles intent into metadata. No agent ever touches a raw entity-graph blob.

The invariant: the AI writes the IR; deterministic builders write the metadata; the verifier tries to break it; the reconciler applies it draft-first with a reviewable plan. Quality is enforced by gates, not hoped for.
A1

The App-Spec IR · seven slices, one blackboard

The IR is the typed contract between agents. Each slice has a single owner and a strict shape the engine verify step validates.

SliceOwnerShape (condensed)
domainkf-ba{ personas[], journeys[], entities[], business_rules[] } — every item evidence-linked to the BRD
understandingkf-comprehensionfor an existing app — static model derived from live metadata + sandbox probes
architecturekf-architect{ flows[], er_map[], roles[], journey_flow_map[], build_order[] }
data_modelkf-data-architect{ flows:{ <id>:{ fields[], references[], child_tables[], computed[], views[] } } }
workflowkf-workflow-designer{ processes:{<id>:{steps[]}}, cases:{statuses[],transitions[]}, slas[], notifications[] }
securitykf-security-designer{ roles:{<id>:{flows:{<id>:{scope,fields{},steps{},statuses{}}}}}, data_scope }
experiencekf-experience-designer{ roles:{<id>:{ landing, nav[], dashboard{tiles[]}, pages[] } } } — tiles DERIVED, never authored

Slices lower from abstract to concrete: domain → architecture → data_model / workflow / security → experience. Each later agent reads everything above it; data_scope in security is the canonical map dashboards and views must reuse — so scope is defined once and applied everywhere.

A2

The pipeline · who → what → build → secure → present

The orchestrator (/author-app) runs the agents in a canonical order that makes references resolve — roles before the things that reference them, masters before referencers, pages last. Every step is gated by the verifier; the run does not advance until it passes (or the user waives a flagged risk).

kf-ba — BRD → domain (personas, journeys, entities, rules). asks clarifying Qs only for true gaps
kf-architect — domain → architecture: the ER map, which entities become form / process / case / list, child-table splits, the role list, journey→flow paths, and the build_order.
Roles first (data models & permissions reference them) → create app + roles + grant access.
kf-data-architect — data_model: fields/types/required, references (target + lookup/hidden + filter), child tables, computed formulas. Masters/lists created here so refs resolve.
kf-workflow-designer — workflow: process steps + assignees, case statuses + transitions, SLAs, notifications — proven reachable & deadlock-free.
kf-security-designer — security: field/step/status permission matrices per role + the canonical data_scope (my-items / my-team / all). No lockouts.
kf-experience-designer — experience: each role's landing, role-gated nav, and DERIVED dashboards (role × scope × workflow × reports) — pages LAST.
Between every step sits kf-verifier — it runs engine verify and then adversarially tries to break the slice just produced (lockouts, deadlocks, unreachable states, empty filters, dangling refs). It is a gate: the pipeline does not advance until it passes.

A4

The gates · three layers of assurance

Correctness is enforced at three altitudes — per slice, per app, and per journey. Nothing reaches production unproven.

Per slice · kf-verifier

After each step, adversarially tries to break the new slice — lockouts, deadlocks, unreachable states, empty filters, dangling refs. Pipeline stalls until green.

Per app · coherence critic

Above the per-slice verifiers: does the whole app hang together per persona & per goal? Meaningful landings, correct scope, no orphans, completeness matrix.

Per journey · acceptance

Behavioural proof in a sandbox: each persona actually creates an item and advances it through the workflow, asserting state, permission, and visibility at every step.

A5

Operating principles & entry points

Principles

Intent, not metadata

The AI writes the IR; the engine compiles it. No agent edits a raw entity-graph blob.

Evidence-linked

Every IR item traces to a journey or business rule — no invented requirements.

Dry-run & draft-first

Always show the plan; build into drafts; never auto-publish to production.

Live app is the truth

For existing apps the reconciler proposes minimal reviewable diffs — never a regenerate, never overwriting dev edits.

Pipeline A · deterministic builders

A Kissflow app is a flat entity-graph blob keyed by Id, with a Root pointer and Parent→Child id-array relations. buildApp() turns the IR into that blob with no AI in the loop — pure, testable functions.

buildForm

Sections → rows → columns → fields. Type-aliases (YesNo→Boolean), wires unlinked Selects to lists/masters, defaults Reference lookups.

addChildTable

Embeds childOf forms: Model→Row→Column(Model)→child Model→Row→Column(Field)→Field.

addWorkflow

ProcessDef → Activities (Start/User/End) → per-field, per-step Permissions + step Resources (assignees).

buildPage

Cards → the intermediate format → Kissflow's real transformer.py → rendering-correct page metadata.

buildPermission

Per-(role, model) access cells in the export-verified Permission shape.

lists & masters

Value lists (Select sources) and master forms (Reference targets), built first so refs always resolve.

The entity graph a process becomes

Model "BT Request" ← the process (Root) ├─ Model::Row │ ├─ Column (Type=Section) → fields… parent form layout │ └─ Column (Type=Model) "Attendees" child table │ └─ Model "Attendees" │ └─ Row → Column (Type=Field) → Field "Select attendee" (Reference→Employee Master) ├─ Model::ProcessDef │ └─ Activity "Reporting Manager Approval" (UserTask) │ ├─ Permission {Column, Editable|ReadOnly} incl. child-table columns ✔ │ └─ Resource {AppRole: Reporting_Manager} └─ Model::Field × 42 amount, dates, selects, references…
03

Pipeline A · applying it live (resiliently)

applyIR() walks the built artifacts and creates them in the real app over REST — then publishes, grants access, and wires navigation. Every call retries transient failures and never throws, so one hiccup can't abandon the run half-built.

Create flows — one POST per list, master form, and process. POST /flow/2/{acct}/{type}
Push + publish metadata — PUT the entity blob into each draft, then publish. PUT …/draft → POST …/publish
Create roles & build the role→id map. POST /app_role/2/{acct}
Grant access — process Initiate [], report "View report" ["View"], derived from who can see each page (page.role + nav VisibleTo).
Build pages — each intermediate → the real transformer → publish to its page id.
Wire navigation — a Menu per process → sub-menus (My Requests / Approvals / All), role-gated by VisibleTo. Built LAST (pages regenerate nav).
Set role Preference — DefaultPage + DefaultNavigation, so each role lands on its dashboard instead of a blank screen.
Verify — read-after-write via explore; assert every flow is nested + Live.
The "role sees nothing" trifecta: a role only experiences its app when all three exist — (1) a role Preference {DefaultPage, DefaultNavigation}, (2) a nav SubMenu.VisibleTo entry, and (3) flow + report member access. Miss one and the screen is blank. applyIR guarantees all three.
04

Pipeline B · reading the live app back

The runtime UI never hardcodes anything about the app — it learns it. Three CLI tools turn the live Kissflow app into a buildable description.

kf-sync

Pulls data models + fields, roles, the app's display name, and the full nav tree (menus → submenus → page → VisibleTo roles). → lib/kf-schema.json + kf-context.md.

kf-import-page

Distills each page's builder layout into a clean spec — components, their data bindings (flowId/viewId), and section grouping. → lib/pages/*.json.

kf-gen-page

Composes rich, varied React pages from the specs + schema. Emits src/pages/<dir>/*.jsx, a shared _metrics.js engine, and lib/nav.json (the role-gated tree).

GQM & Kimball — the two frameworks behind every dashboard

Most generated dashboards look samey because they show the data that happens to exist. We don't compose by guesswork — we borrow two decades-old, battle-tested frameworks. One decides what is worth showing; the other generates the breakdowns for free. Here's what each is, and exactly how we use it.

GQM · Goal → Question → Metric

What it is

Goal-Question-Metric is a measurement framework from Victor Basili and the NASA Software Engineering Lab (1980s). It is strictly top-down: first state a Goal (the purpose), then derive the Questions that tell you whether the goal is being met, and only then choose the Metrics that answer those questions. The discipline it enforces: you measure what answers a real question tied to a goal — never "whatever is easy to count."

How we use it

We invert dashboard design with it. The #1 failure mode of a generated dashboard is dumping every available field into a widget. Instead, the page's role intent — inferred from which views it binds (myitems / mytasks / admin) — is the Goal. From that goal we plan the questions, and the metrics that answer them become the hero MetricCards. Three roles → three goals → three genuinely different pages.

Worked example · the approver
G/Q/MFor an approver
GoalClear my approval queue without letting risk slip through.
QuestionWhat's waiting on me? · How much value is at stake? · What's aging past SLA?
MetricPending mine · Value-at-risk (Σ amount of open items) · Avg age · SLA breaches

Kimball · dimensional modeling

What it is

Ralph Kimball's dimensional modeling is the standard way data warehouses are designed. You model the business as facts (the measurable events) surrounded by dimensions (the descriptive context you slice by) — a star schema. Its whole purpose is to make "measure BY dimension" analysis natural: revenue by region, spend by category, count by status.

How we use it

The key realization: a Kissflow app is already a star schema — we just read it off the metadata, no modeling required.

Travel CategoryCompany CodeFunctionCost Center

From that star, the rollups are declared by the metadata — we don't guess which chart to draw:

Σ Grand Total by Travel Category → donut Σ Grand Total by Function → ranked bars Σ Grand Total over Request Date → area trend count by stage → pipeline

Classifier in code: star(fields) picks the measure (amount-named / currency, never a SequenceNumber), the dimensions (Reference/Select, minus noisy id/name fields), and the date. rollup(items, dim, {measure}) then produces each breakdown — per flow, so a multi-flow page gets one breakdown per flow.

How they combine: GQM picks which metrics and dimensions matter for this role; Kimball turns those into measure-by-dimension rollups automatically; Grammar of Graphics picks the mark (donut/bars/line); Shneiderman's mantra orders the layout (hero → primary → rollups → queue). Content from GQM, structure from Kimball, encoding + layout from the rest — every number computed live from getItems().

One honest constraint

The dev runtime reads the app over REST with an integration key. That surface is intentionally narrow for processes.

Works over REST (dev preview)

Counts · workflow stage / pipeline · status · SLA & aging · the nav · actions · charts — all live.

Needs the in-product runtime

Process business-field values (dimensions + amounts) — /myitems projects only Name + system fields to an integration key. They render when the same pages run inside Kissflow, where the SDK has a real session.
